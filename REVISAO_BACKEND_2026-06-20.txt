1. VISÃO DO PROJETO
------------------------------------------------------------------------------

ApoloChristus é uma aplicação web que agrega tudo sobre Cristianismo —
Bíblia (várias traduções e línguas), Pais da Igreja, apócrifos, credos e
confissões, léxico/interlinear original — numa única plataforma pesquisável.

Motivação central (do utilizador, registada em memória):
  Resolver 3 problemas pessoais de pesquisa sobre Cristianismo:
  1. Não saber ONDE pesquisar (informação espalhada por dezenas de sites)
  2. Não saber O QUE pesquisar (falta de pontos de entrada/descoberta)
  3. Não saber se a informação encontrada está CORRETA (falta de fontes
     primárias e de transparência sobre proveniência)

Isto orienta decisões de design: agregação (resolve 1), cross-references
+ citações patrísticas + estrutura de navegação (resolve 2), fontes
primárias + campo source_url/license em quase todas as tabelas (resolve 3).

Comparação com Logos Bible Software (discutida em sessão): ApoloChristus
não compete em profundidade de ferramentas, mas ocupa um nicho real —
grátis, aberto, multilingue, com Patrística como pilar central (não um
extra pago) — que nem o Logos (pago, fechado) nem o BibleGateway/YouVersion
(grátis mas raso) cobrem.

Stack: React + Vite (frontend, ainda por construir) · Supabase/Postgres
(BD) · Python (pipeline de ingestão) · GitHub Desktop (workflow de Git).

5.1 BÍBLIA (bible_fetcher.py) — 6 versões, 161 281 versículos
-----------------------------------------------------------
Fontes: wldeh/bible-api (GitHub) para en-kjv/en-asv/grc-grctr/hbo-wlc;
thiagobodruk/biblia (GitHub) para pt-aa/pt-acf.

Bugs reais encontrados (o código nunca tinha sido testado contra as
fontes reais antes desta sessão):
  - Endpoint CDN jsdelivr bloqueado (repo >50MB) — mudado para
    raw.githubusercontent.com
  - IDs de versão inventados (por-ARC, eng-KJV...) não existem — IDs
    reais descobertos via GitHub API
  - NÃO existe nenhuma Almeida no wldeh/bible-api — só inglês, grego,
    hebraico. Português veio de fonte alternativa (thiagobodruk/biblia)
  - Formato JSON diferente do assumido ("data" em vez de "verses")
  - Nomes de livro variam por idioma (inglês: nomes completos; grego/
    hebraico: nome nativo) — mapas de tradução construídos por idioma
  - BUG DE ENCODING WINDOWS: Path.write_text() sem encoding="utf-8"
    corrompia acentos — corrigido em TODOS os ficheiros do pipeline
  - Versículos DUPLICADOS na fonte en-kjv (cada um aparecia 2x) —
    deduplicação adicionada
  - GitHub duplica entradas pasta+ficheiro na listagem de diretório
    (contagem de capítulos a dobrar nos deuterocanónicos)
  - Adições gregas a Ester (ESG) numeradas como capítulos 10-16
    (continuação do Ester hebraico), não 1-7

Validação: en-kjv e en-asv batem exatamente com o número clássico
31 102 versículos; grc-grctr bate com o número conhecido do NT grego
(7 957); confirma correção da extração.

Deuterocanónicos: 14 livros (1ES,2ES,TOB,JDT,WIS,SIR,BAR,BEL,ESG,MAN,
1MA,2MA,S3Y,SUS), 5 718 versículos, só disponíveis em en-kjv. Flag
is_deuterocanonical na tabela verses.

Licenciamento: en-kjv/en-asv/grc-grctr/hbo-wlc = domínio público
confirmado. pt-aa/pt-acf = licença NÃO confirmada formalmente

5.2 PAIS DA IGREJA (patristics_fetcher.py) — 65 autores, 341 obras, 67 604 secções
-----------------------------------------------------------------------------------
Fonte: New Advent (newadvent.org/fathers), coleção ANF/NPNF, domínio
público (traduções séc. XIX).

Processo: catálogo completo gerado programaticamente a partir do índice
real do site (não inventado) — guardado em fetchers/patristic_catalog.json.
Cobre apostólicos, ante-nicenos, nicenos, pós-nicenos — essencialmente
toda a coleção disponível nessa fonte.

Bugs reais encontrados:
  - Seletor HTML errado (div.text não existe — é div#springfield2)
  - Secções marcadas por <h2>Chapter N.</h2>, não por <a name="N">
  - VÁRIOS URLs do catálogo original apontavam para obras ERRADAS
    (ex: "Carta aos Efésios" apontava para outro texto completamente
    diferente) — corrigidos um a um consultando o índice real
  - Muitas obras não têm o texto numa única página — são índices que
    apontam para subpáginas (livro→capítulo); implementado scraper
    recursivo genérico que segue páginas de índice automaticamente,
    detetando por padrão de URL (prefixo numérico partilhado) em vez de
    por palavras-chave de texto (mais robusto, apanhou casos atípicos
    como "THE SIEGE OF NISIBIS" sem precisar de regex específico)
  - BUG DE PERDA DE DADOS: section_num repetia-se quando um capítulo
    tinha vários parágrafos (violava UNIQUE(work_id,section_num); um
    upsert teria APAGADO parágrafos silenciosamente) — corrigido para
    contador sequencial sempre único
  - Rodapé "About this page" (info de contacto do site) estava a ser
    apanhado como conteúdo da obra — filtrado
  - Hermas "O Pastor": vários rótulos de secção apontavam para a MESMA
    página (FIRST VISION, SECOND VISION...) — sem deduplicar, duplicava
    o texto

Autores incluídos: Inácio, Policarpo, Clemente de Roma, Justino Mártir,
Ireneu, Tertuliano, Orígenes, Clemente de Alexandria, Hipólito,
Atanásio, Basílio, Gregório Nazianzeno, Gregório de Nissa, Cirilo de
Jerusalém (NÃO Cirilo de Alexandria — não disponível no New Advent),
Crisóstomo, Agostinho, Jerónimo, Ambrósio, Leão Magno, Gregório Magno,
João Damasceno, e mais ~45 autores menos conhecidos (lista completa no
catálogo).

BUG DE INFRAESTRUTURA (loader): upsert sem on_conflict explícito usa a
PRIMARY KEY (BIGSERIAL, nunca em conflito) — cada re-execução duplicava
TODAS as linhas em vez de atualizar. Corrigido em todo o load_to_supabase.py
para usar as chaves naturais (on_conflict="work_id,section_num" etc.)
— relevante para qualquer tabela nova que se adicione no futuro.

5.7 GEOGRAFIA (geography_fetcher.py + geography_confidence_fetcher.py) — 1 232 locais
------------------------------------------------------------------------------------------
Fonte inicial: OpenBible.info merged.txt (TSV simples, "versão 2007
simplificada" confirmada pelo próprio site) — 1 232 locais com
coordenadas (resolve referências indiretas via campo "Root", ex:
"Abarim" -> coordenadas de "Mount Nebo"). CC-BY 4.0.

Bug: GitHub duplica entradas pasta+ficheiro também aqui inicialmente
mal-entendido como dado real (42 linhas legitimamente sem coordenadas
por terem localização desconhecida/disputada, ex: "Éden" — não é bug,
é honestidade dos dados).

MELHORIA POSTERIOR (mesma sessão, depois de pergunta do utilizador
"isto tem base histórica?"): descoberto que o merged.txt é só a versão
simplificada; existe um dataset MUITO mais rico em JSON Lines
(github.com/openbibleinfo/Bible-Geocoding-Data) com sistema de pontuação
académico completo (múltiplos caminhos de identificação, regressão
linear por década de publicação 1969-2020, taxonomia de tipos de voto).
Decisão consciente (confirmada com o utilizador, "profissionalmente e
academicamente"): NÃO replicar o sistema completo — usar só time_total
(que a própria documentação do dataset designa como o número-resumo
oficial) convertido para confidence_pct (0-100, com clamp porque a
regressão pode extrapolar fora de [0,1000]) + identification_sources
resolvidas via source.jsonl.

Correspondência por nome: 1050/1232 (85%) — o resto não bateu porque o
dataset novo desambigua locais homónimos com sufixos próprios (ex:
"Gath 1/2/3") que não alinham com os do merged.txt antigo; deixados sem
confiança/fontes em vez de arriscar correspondência errada.

BUG REAL DE POSTGRES (relevante para o futuro): um upsert PARCIAL (só
name+confidence_pct+sources) falhava sempre com erro NOT NULL em
lat/lon, MESMO para linhas já existentes — porque o Postgres valida as
colunas NOT NULL do "candidate row" de um INSERT...ON CONFLICT ANTES de
decidir se há conflito. Resolvido com uma função SQL
(bulk_update_place_confidence) que faz UPDATE direto via
jsonb_to_recordset em vez de upsert. Regra geral: upserts parciais em
tabelas com colunas NOT NULL sem default precisam de UPDATE explícito,
não upsert.

5.9 MORFOLOGIA / INTERLINEAR (interlinear_fetcher.py) — 425 437 palavras
-------------------------------------------------------------------------------
Fonte: STEPBible-Data, ficheiros "Translators Amalgamated" (TAGNT grego
NT, TAHOT hebraico AT) — desenhados para crítica textual (incluem TODAS
as variantes de manuscrito), por isso cada posição de palavra pode ter
várias linhas; mantida só a leitura mais bem atestada por posição (flag
de edição mais "completa") — suficiente para leitura, não para aparato
crítico completo.

Grego: 141 720 palavras (bate com o número académico conhecido do NT).
Hebraico: 283 717 palavras (bate com o número académico conhecido do AT).
66 livros = Bíblia completa, códigos 100% compatíveis com os já usados
no projeto (sem necessidade de mapeamento).

Bug: colunas "dStrongs" e "Grammar" vêm SEPARADAS no ficheiro hebraico,
mas COMBINADAS (com "=") no ficheiro grego — assumir o mesmo formato
para os dois deixava o campo "grammar" do hebraico sempre vazio.
Hebraico tem palavras compostas prefixo+raiz (separadas por "/") com
múltiplos Strong's por palavra — schema usa TEXT[] para strong_numbers.

5.10 CITAÇÕES PATRÍSTICAS (citations_fetcher.py) — 30 157 citações
--------------------------------------------------------------------------
ÚNICA tarefa desta lista que NÃO é fetch externo — extrai citações
bíblicas de dentro do texto patrístico JÁ carregado (67 604 secções),
por regex, e valida cada candidato contra os 161 281 versículos reais
antes de guardar (descarta falsos positivos).

Padrão de citação descoberto nos dados reais: o scraping do New Advent
deixou referências bíblicas coladas no texto corrido (ex: "...all in
all. 1 Corinthians 15:24-28 If the So...") — resíduo de links HTML
achatados em texto simples durante a extração original.

Decisão de qualidade: livros que exigem dígito ordinal para desambiguar
(Corinthians, Timothy, Peter, Thessalonians, Kings, Samuel, Chronicles,
Maccabees) são IGNORADOS se o dígito não for capturado, em vez de
adivinhar 1 vs 2. "John" sem dígito = Evangelho (não ambíguo, caso
correto de não exigir dígito).

Validação de qualidade: os versículos mais citados (João 1:1 com 89
citações, João 1:14, João 14:6, Filipenses 2:6, Génesis 1:26) são
exatamente os versículos teologicamente centrais nos debates
trinitários/cristológicos dos primeiros séculos — forte confirmação de
que a extração está a apanhar citações reais, não ruído.

Função SQL: verses_cited_by_fathers(book, chapter, verse) — devolve
quais Pais/obras citaram um versículo, já testada e a funcionar.

6. PADRÕES DE BUGS RECORRENTES (úteis para qualquer trabalho futuro)
------------------------------------------------------------------------------

1. NUNCA confiar em código/catálogos gerados sem testar contra a fonte
   real — em TODOS os 3 fetchers originais (Bíblia, Patrística,
   Apócrifos) o código nunca tinha corrido contra as APIs/sites reais e
   tinha bugs sistemáticos (URLs errados, seletores errados, formato de
   dados errado).
2. Path.write_text()/read_text() no Windows precisa SEMPRE de
   encoding="utf-8" explícito, senão corrompe acentuação.
3. GitHub Contents API duplica entradas pasta+ficheiro do mesmo nome na
   listagem de diretório — sempre filtrar por extensão (".json", etc.)
   ao contar ficheiros.
4. section_num / chaves de unicidade: nunca usar um valor "semântico"
   (nº de capítulo, posição relativa) como chave única se o mesmo valor
   pode repetir-se dentro do agrupamento — usar sempre um contador
   sequencial puro.
5. upsert() do Supabase/PostgREST: SEM on_conflict explícito usa a
   PRIMARY KEY (nunca em conflito em tabelas com BIGSERIAL), causando
   duplicação silenciosa em vez de atualização. SEMPRE especificar
   on_conflict com a chave natural da tabela.
6. upsert() PARCIAL (sem todas as colunas NOT NULL) falha mesmo para
   linhas já existentes — o Postgres valida NOT NULL antes de resolver
   o conflito. Usar UPDATE explícito (ou uma função RPC) para
   atualizações parciais.
7. Antes de assumir que uma fonte "não tem X", verificar a sério (ex:
   geografia — parecia só ter dados simples, mas tinha um dataset muito
   mais rico disponível só não óbvio à primeira vista).
8. Repositórios GitHub mudam de dono/local (301 redirect) — seguir o
   redirect via API em vez de assumir que um URL antigo de documentação
   ainda é válido.
